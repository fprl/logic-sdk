---
title: Scope
description: Who is calling and from where, bound once per request, job or test.
---

The scope answers "who and where": the actor, the account or tenant, the locale, a request id. It never holds "what": booking ids and form data are input.

It's your own type. The library defines no fields.

```ts
type Base = { accountId: string; locale: string };

// Signed in or not
export type Scope =
  | (Base & { actor: null })
  | (Base & { actor: { id: string; role: Role } });
```

Make it a union of signed in and signed out, so [policies](/docs/concepts/authorization#policies) can narrow it.

- **Bind it once** per request, job or test with `registry.as(scope)`. Every nested call inherits it.
- **Change it for one call** with run options: `ctx.run(fn, input, { scope: { ...ctx.scope, locale: "es" } })`. Pass the whole scope, for that call and everything it runs; it isn't merged. So it's always one of your variants: a patch like `{ kind: "system" }` could build a scope that passes a policy while missing the fields it promises.
- **Listeners get the scope** of the call that emitted the event, so a confirmation email goes out in the guest's locale.
- **Keep it JSON.** It travels with events, so it must be serializable. Policies are plain functions in `policies.ts`, like `member(scope)`, not methods.
- **Jobs rebuild it.** With an adapter that keeps jobs (a database queue, an outbox, Cloudflare), `jobs.scope.load` rebuilds the scope when each one runs, with today's roles: see [Jobs](/docs/concepts/jobs#who-a-job-runs-as). On `inProcess()` a listener sees the scope as it was at emit, flags included. See [Feature flags](/docs/concepts/feature-flags).

## The system

Work nobody asked for in a request, like a [cron](/docs/concepts/crons), still runs as a scope. Make it a variant of your type, not a fake user:

```ts
export type System = Base & { actor: null; system: string }; // names what's acting: "orders.sendDigest"
export type Scope = (Base & { actor: null }) | (Base & { actor: Actor }) | System;

export const asSystem = (name: string, accountId: string): System => ({ actor: null, system: name, accountId, locale: "en" });
```

```ts
// policies.ts: what the system may do, spelled out
export const system = (s: Scope): s is System => "system" in s;
export const staffOrSystem = (s: Scope) => staff(s) || system(s);
```

- **It has no actor,** so `signedIn` and `staff` still say no: every grant to the system is explicit.
- **A request never builds it.** Only your crons and scripts do.
- **If you set `jobs.scope`, `store` and `load` must handle it.** A cron's own run doesn't use them (its scope comes from your code), but an event its mutation emits, or a call it schedules, stores the system scope like any other: keep the `system` field in `store` and rebuild it in `load`.
- **Phoenix does the same:** its scope is your own struct, with `user: nil` and extra fields for a scope "not tied to a user". Convex passes no auth to scheduled functions at all.

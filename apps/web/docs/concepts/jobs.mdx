```ts
const database = drizzleAdapter(db);

createRegistry({
  modules,
  database,
  jobs: {
    adapter: databaseQueue(database),                           // where jobs go; default inProcess()
    scope: {
      store: (s) => ({ userId: s.user?.id ?? null, accountId: s.accountId }), // what's saved with each job
      load: (saved) => scopeFor(saved),                         // rebuilt when it runs; null discards it
    },
  },
});
```

A **job** is one piece of work that runs after your transaction commits. It comes in three kinds, and all of them go through the same `jobs` slot:

| Kind | Where it comes from | |
|---|---|---|
| A listener's share of an event | `ctx.emit(event, payload)` in a mutation: one job per listener | today |
| A scheduled call | `ctx.schedule(fn, input, { at })` in a mutation: run this function once, later | today |
| A cron's run | `cron({ schedule, run, scope })`: run this function on a schedule ([Crons](/docs/concepts/crons)) | today |

If you've used Rails, Laravel or Oban, a listener is what you'd write as a job class, and the `jobs` slot is their queue adapter.

## Adapters

The adapter decides where a job waits and what survives a crash.

```txt
inProcess()  default, zero infra
  mutation ─ commit ─► run the listeners in this process
  lost if the process dies after commit

databaseQueue(database)  durable, Postgres or SQLite: your database is the queue (Laravel's database driver)
  mutation ─ insert a row ─ commit ─► your app runs it, deletes the row
                                   └► failed or crashed: registry.jobs.sweep() runs it again

cloudflareQueue(env.JOBS)  a queue alone (Laravel's SQS driver, after commit)
  mutation ─ commit ─► send it ─► your consumer ─► registry.jobs.run(job)
                    └► the process died before the send: lost

outbox(database, cloudflareQueue(env.JOBS))  durable, a table in front of a queue (the outbox pattern)
  mutation ─ insert a row ─ commit ─► send it, delete the row ─► your consumer ─► registry.jobs.run(job)
                                   └► the send failed or crashed: registry.jobs.sweep() sends it again
  after the handoff, the queue owns retries, concurrency and its dead-letter queue
  planned behind an outbox: Vercel Queues, Redis (BullMQ), Inngest

pgBoss(boss)  durable, Postgres: pg-boss inserts inside your transaction
  mutation ─ pg-boss insert ─ commit ─► work(registry, boss) ─► registry.jobs.run(job)
                                     └► a throw: pg-boss retries it with backoff; failed for good: kept as failed
```

- **Which one:** `databaseQueue` unless you need what a queue gives you (its own consumers, more throughput). Then the queue alone if losing a job on a crash is fine, and behind an `outbox` if it isn't.
- **Why an outbox goes first:** a queue that isn't your database can't join your transaction. Sending after commit loses the job if the process dies in between, which is the Rails and Laravel `after_commit` default. Writing a row in the transaction closes that gap, and the queue then adds what it's good at.
- **A job is done before the jobs it queued run,** as in Laravel: a listener whose mutation emits an event has its row deleted before that event's listeners start, after the jobs queued alongside it. A crash in one of them can't run the first again.
- **`databaseQueue` and pg-boss need no outbox:** each lives in your database, so its insert commits or rolls back with your writes, like Oban.
- **One page per adapter:** [database queue](/docs/adapters/drizzle#database-queue) (or [with another ORM](/docs/adapters/other-orms)), [outbox](/docs/adapters/drizzle#outbox), [pg-boss](/docs/adapters/pg-boss), [Cloudflare](/docs/adapters/cloudflare).
- **The adapter's own options go in its factory:** `databaseQueue(database, { lease, backoff })`, `outbox(database, queue, { maxAttempts })`. What every adapter honours goes in `jobs` (today, `scope`).

## What each one guarantees

| | Crash right after commit | Job failed for good | `delay`, `ctx.schedule` | `replace` | A cron ticked twice |
|---|---|---|---|---|---|
| `inProcess()` | lost | only `onError` | refused (one try) | no | runs twice |
| `databaseQueue` | kept | kept as `failed` | yes | yes | runs once |
| `cloudflareQueue` alone | lost, if not sent yet | only `onError` | up to 24 hours | no | runs twice |
| `outbox` + Cloudflare | kept | kept as `failed` | yes | yes | runs once |
| `pgBoss` | kept | kept for 7 days | yes | yes | runs once |

All but `inProcess()` can run a job twice. On Cloudflare, "failed for good" needs [`max_retries`](/docs/adapters/cloudflare#set-max_retries-to-at-least-your-largest-attempts) at least your largest `attempts`. These are tested on Postgres and against a fake Cloudflare queue. Deployed Workers, Queues and Vercel aren't tested yet.

## Running, sweeping, retrying

```ts
await registry.jobs.run(message.body, { attempt: message.attempts }); // a queue consumer
await registry.jobs.sweep();                                          // a cron or an interval (databaseQueue, outbox)
await registry.jobs.retry(id);                                        // put a failed job back in line
```

- **`run` resolves `"done"`, `"failed"` or `"discarded"`: acknowledge all three.** `failed` means it's over: the listener is out of `attempts`, or retrying can't help (a domain error other than `conflict`, or a payload that no longer matches its schema). It throws when the listener has tries left and a retry might help. Every failure goes to `onError` with `source` (the listener, cron or function), the `job` itself, the attempt, and `outcome`: `"retry"`, `"failed"` or `"discarded"`, so you can alert on the last one only.
- **`sweep` runs what's due:** retries whose backoff is over, and jobs whose runner crashed. Adapters that store nothing resolve zeros, and so does pg-boss, which maintains itself, so one cron handler works with any of them.
- **`retry` only revives failed jobs** and returns whether it did. A pending one belongs to its runner, and resetting it could run it twice at once. It throws on `inProcess()`, which stores none.

## Attempts and delay

```ts
export const sendReceipt = listener({
  event: () => orders.placed,
  attempts: 5, // tries in total, the first included
  delay: 60,   // seconds after the event before the first try
  async handler(ctx, { orderId }) { ... },
});
```

- **`attempts` defaults to 1,** like Rails (no `retry_on`), Laravel (`--tries=1`) and Solid Queue. A retry repeats side effects, so you opt in per listener, like Laravel's `$tries`. Oban defaults to 20 and pg-boss to 3.
- **Out of attempts, the job is `failed`:** kept by `databaseQueue`, `outbox` and pg-boss, retried with `registry.jobs.retry(id)`.
- **A last try that never finished** (the process crashed, or the job ran past the time `databaseQueue` keeps extending its lease) is `failed` without running again, as Laravel's worker does.
- **Stamped on the job when it's queued,** like Laravel and Oban: a deploy that changes `attempts` applies to jobs queued after it.
- **`delay`** is stamped on the job as `runAt`. `databaseQueue` and `outbox` keep the row until then, pg-boss gets it as `startAfter`, and Cloudflare as `delaySeconds`.
- **`inProcess()` tries once and can't hold a job.** What throws is `failed`, whatever its `attempts`. And `createRegistry` refuses a listener with a `delay` there, rather than run it early (Laravel's sync queue drops the delay) or lose it on a restart. Use `databaseQueue(database)`. Cloudflare alone holds up to 24 hours.

## Scheduled calls

```ts
export const confirm = mutation({
  async handler(ctx, { bookingId }) {
    // ...confirm it
    ctx.schedule(guests.remind, { bookingId }, { at: dayBefore(booking.checkIn) });
    ctx.schedule(holds.expire, { bookingId }, { delay: 15 * 60 }); // seconds
    ctx.schedule(payments.capture, { bookingId }, { delay: 60, attempts: 3 }); // an API call: give it tries
  },
});
```

- **Run a mutation or action once, later,** at a time this mutation decides. A listener's `delay` is the same for every event; this one is yours per call.
- **Only from mutations:** it's committed with the transaction, so a booking that rolls back never leaves a reminder behind, as in Convex. An action or listener that wants to schedule runs a mutation that does.
- **`{ at }` or `{ delay }`, not both:** a `Date` (from `ctx.now()`), or seconds like a listener's `delay`. It returns the job id. Due now (`delay: 0`, an `at` already past) runs right after commit, like a listener.
- **`replace: key` when it can change:** a newer call to the same function with the same key replaces the one still waiting, its input, time and tries. Move a booking's dates and the reminder moves with it, instead of two going out:

  ```ts
  ctx.schedule(guests.remind, { bookingId }, { at: dayBefore(booking.checkIn), replace: bookingId });
  ```

  A call that already started isn't touched; the new one runs on its own. A call waiting out a retry's backoff has started too. With an `outbox`, started means handed to the queue. The replaced call's id is gone, so `retry` with it returns `false`. Like Oban's `replace` and Laravel's `DebounceFor`. It needs an adapter that can replace (`databaseQueue(database)`, `outbox(database, queue)` or `pgBoss(boss)`); `cloudflareQueue` alone can't take back a message it sent, so it's refused.
- **No cancel.** It runs whatever happens meanwhile, so the function checks that its reason still holds ("is the booking still confirmed?"). Convex can cancel, but a call that already started keeps running, so the check is needed anyway.
- **It runs as the scheduling mutation's scope,** through `jobs.scope` like a listener; the function's `authorize` and input schema check it when it runs (the input is also checked at commit).
- **`attempts`: one try by default,** like a listener. Give an action that calls an API a few (`attempts: 3`); retries back off like a listener's.
- **Due now, it's a hop in the chain:** a function that schedules itself with no delay stops at `maxEventDepth`, like a [listener loop](/docs/concepts/events). One that waits starts a new chain.
- **It needs an adapter that holds jobs:** `databaseQueue(database)`, `outbox(database, queue)` or `pgBoss(boss)`. `ctx.schedule` throws on `inProcess()`.
- **Test it** with `t.jobs.scheduled` and `t.jobs.drain({ until })`: see [Testing](/docs/testing#jobs-in-tests).

## Ids

A job stores the id of the listener it runs and the event it carries. Rename the export while jobs are queued and they can't find their code: each try fails until their attempts are used, like a missing class in Laravel. Then they're failed, and where your adapter keeps them, `registry.jobs.retry(id)` runs them once the code is back. Give it an `id` before you rename, and queued jobs keep finding it:

```ts
// notifications/listeners.ts
export const sendAll = listener({
  id: "send",                    // stays notifications.send, whatever the export is called
  event: () => conversations.messageReceived,
  async handler(ctx, payload) { ... },
});
```

- **Optional.** The default is the export name.
- **Local to the module:** in a `notifications` module, `id: "send"` is `notifications.send`. Write `"send"`, not `"notifications.send"`: the module key is added for you.
- **On every definer:** `query`, `mutation`, `action`, `event`, `listener`. Events need it as much as listeners, and scheduled calls store function ids.
- **Unique:** a clash throws at `createRegistry`.
- **Deploy new code before what calls it.** In a rolling deploy, an old process can pick up a job for a listener only the new code has, and that costs the job a try. With attempts left the new process runs it later; with the default of one it's failed. Give the listener `attempts`, or ship it one deploy before the code that emits its event.
- **Where else it shows:** the [fetch adapter](/docs/adapters/fetch)'s routes and error codes (`notifications.send.forbidden`) use the id. oRPC routers and AI tools keep the export name, because their types come from your modules' export names.

## Who a job runs as

A job runs as the scope that emitted or scheduled it, so policies check it again and tenant-scoped helpers keep working. A job that waits in a table or a queue would run with the roles of the day it was queued, so every adapter but `inProcess()` needs `jobs.scope.load`. TypeScript asks for `scope`, and `createRegistry` throws without `load`:

- **`inProcess()` needs nothing:** it runs each job right after commit, so no scope waits.
- **Keeping the scope as it was is a choice you write down:** `load: (saved) => saved`. Fine for a scope with nothing that changes (an id and a locale); not for roles.
- **`store` picks what's saved:** ids, not whole objects. It has to be plain JSON, and that's checked when you emit, in tests too.
- **`load` rebuilds the scope when the job runs,** so every `ctx.run` checks policies against today's roles.
- **`load` returning `null` discards the job** (reported to `onError`, deleted from the table). Use it when what the job ran as is gone, like an offboarded account. Rails' `discard_on` and Laravel's `DeleteWhenMissingModels` do the same. Check membership here too: a user who left the account gets `null`.
- **Keep the system:** a [system scope](/docs/concepts/scope#the-system) (a cron's) is stored like any other, so `store` keeps its `system` field and `load` rebuilds it.
- **`load` throwing counts as a try,** like the listener throwing: with tries left it's retried, at the default of one it's `failed`. So does returning `undefined`, which is almost always a missing `return`.
- **`store` needs `load`:** listeners run as a scope, not as what was saved. `createRegistry` throws otherwise.
- **`load` runs once per job,** before the listener and outside `wrap`: an event with five listeners loads five times. Write `store` first in the object so TypeScript infers what `load` gets, or annotate its parameter.

The registry applies `scope` in every adapter, `inProcess()` and tests included, so what passes in tests passes in production.

## The contract

For writing an adapter:

- **One job per (event, listener):** `{ kind: "delivery", id, listener, envelope, attempts, runAt? }`, where `id` is `<listener id>@<event id>`, the key queues dedupe on. In a listener, dedupe on `ctx.event.id`, in a record of that listener's own. A failing listener retries alone. `runAt` is set for a listener with a `delay`.
- **`enqueue(tx, jobs)`** runs inside the transaction; **`deliver(jobs, runner)`** after commit (a no-op for a queue whose own workers pick jobs up, like pg-boss). Optional **`sweep(runner)`** and **`retry(id)`** for adapters that store jobs.
- **Three job kinds:** a delivery `{ kind: "delivery", id, listener, envelope, attempts, runAt? }`, a cron run `{ kind: "cron", id, cron, scheduledAt, attempts }` and a scheduled call `{ kind: "call", id, fn, input, scope, attempts, depth, runAt? }`. All are JSON; an adapter stores and sends them without looking inside, except `attempts` and `runAt` if its backend needs them at send time.
- **Every adapter but `inProcess()` needs `jobs.scope.load`:** the registry assumes yours keeps jobs, so `createRegistry` asks the app to rebuild the scope they run as.
- **`replaces: true`** says `enqueue` replaces a waiting call with the same replace key (`replaceKeyOf(job)`: `<fn>@<key>`), one not started yet. Without it, `ctx.schedule` with `replace` is refused.
- **`holds: true | { max }`** says the adapter can keep a job until its `runAt` (for at most `max` seconds). Without it, delayed listeners and `ctx.schedule` are refused. **`check({ listeners, database })`** runs at `createRegistry`: refuse what you can't honour. **`fail(job, error)`** keeps a job that failed for good in a queue consumer (`outbox` writes a `failed` row); a consumer can pass its own instead, `registry.jobs.run(job, { attempt, fail })`.
- **The adapter contract isn't stable yet:** it can change before 1.0, until more adapters have used it.
- **Attempts are the core's job:** `runner.run(job, { attempt })` resolves `failed` once the job is out of its `attempts`. An adapter only maps outcomes: `failed` is kept, a throw is retried later.
- **Jobs are JSON.** Payloads and the stored scope are checked at emit, so a `Date` fails in tests instead of after a queue. Send an ISO string and let the schema turn it into a `Date`.
- **Listeners get `ctx.event`** (`id`, `name`, `payload`, `occurredAt`, `attempt`), without the stored scope: `ctx.scope` is the one they run as.

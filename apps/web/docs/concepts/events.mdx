---
title: Events
description: Emitted inside a mutation, delivered to listeners only after commit.
---

```ts
// bookings/events.ts
export const confirmed = event({
  payload: z.object({ bookingId: z.uuid() }),
});

// bookings/mutations.ts, inside a mutation
ctx.emit(confirmed, { bookingId });

// tasks/listeners.ts
/** Create the handover task and email the guest */
export const prepareStay = listener({
  event: () => bookings.confirmed,
  async handler(ctx, payload) {
    await ctx.run(tasks.create, { bookingId: payload.bookingId, title: "Prepare the house" });
    await ctx.services.mailer.send(...);
  },
});
```

- **Delivered only after commit.** A rolled-back mutation emits nothing.
- **Each listener runs like an action**, so every mutation it runs commits on its own.
- **A failing listener never fails the caller.** The error goes to `onError`.
- **`event` is a thunk** (`() => bookings.confirmed`), so two modules can import each other's index without an import-cycle crash.
- **What you emit is what's delivered.** `emit` takes a snapshot of the payload.
- **`emit` returns the event it queued:** `{ id, name, payload, occurredAt }`, the same `id` its listeners see as `ctx.event.id`. A row that must commit with the change (a timeline, an audit trail) can carry it, and a listener finds that row by `ctx.event.id`:

  ```ts
  const event = ctx.emit(commented, { taskId: task.id, commentId: comment.id });
  await ctx.run(timeline.add, { eventId: event.id, name: event.name, taskId: task.id });
  ```
- **Listeners must be idempotent.** They may run again; `ctx.event.id` is the key to dedupe on, in a record of that listener's own: two listeners of one event share its id, so a shared record would make one skip the other.
- **Listeners run with the emitter's scope.** Have them run internal functions, not published ones. See [Authorization](/docs/concepts/authorization#nested-calls-and-listeners).

## Serverless

On serverless platforms, give the registry `waitUntil` so the response returns right after commit and listeners finish afterwards. Without it, `run` waits for the listeners, which is what you want in tests and long-lived servers.

**Next.js:** create the registry once, and hand delivery to `after`:

```ts
import { after } from "next/server";

export const registry = createRegistry({
  modules,
  database: { adapter: database },
  waitUntil: (p) => after(() => p),
});
```

**Cloudflare Workers:** with Hyperdrive, the database client is per request, so the registry is too. Take `waitUntil` from the execution context:

```ts
export default {
  async fetch(request, env, ctx) {
    // Hyperdrive pools connections: a client per request is the recommended setup
    const sql = postgres(env.HYPERDRIVE.connectionString, { max: 5 });
    const registry = createRegistry({
      modules,
      database: { adapter: drizzleAdapter(drizzle({ client: sql })) },
      waitUntil: (p) => ctx.waitUntil(p),
    });
    ...
  },
};
```

**Node:** create the registry once at startup. Without `waitUntil`, a request waits for its listeners, so a graceful shutdown that drains requests drains them too. With the [database queue](/docs/adapters/drizzle#database-queue) you can answer first, `waitUntil: () => {}`: a restart that cuts a listener off is swept up after its lease: retried if it has `attempts` left, else kept as failed for `registry.jobs.retry(id)`. Not with `inProcess()`: there, work still running at a restart is lost.

## Loops

A listener whose mutation emits the event it listens to would loop forever. Delivery stops after **8** hops (`jobs: { maxEventDepth }`) and the loop is reported to `onError`. Real chains are 2 or 3 hops. A call `ctx.schedule` runs right away is a hop too, so a function that schedules itself with no delay stops the same way; one that waits starts a new chain.

## Durability

By default, listeners run in-process right after commit, so a crash between commit and delivery loses them. When that matters, use a durable adapter like the [database queue](/docs/adapters/drizzle#database-queue). How jobs run, retry and who they run as: [Jobs](/docs/concepts/jobs).

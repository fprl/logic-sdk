Every call answers three questions, in this order, each in one place:

| Question | Where it's answered | Fails with |
|---|---|---|
| **Who are you?** | The [scope](/docs/concepts/scope), built at the edge | `unauthenticated` (401), only on session-only mounts |
| **What can you see?** | Account-scoped loading in `data.ts` | `not_found` (404) |
| **What may you do?** | `authorize` for the function, `can*` for the record | `forbidden` (403) |

## Policies

A policy is a plain, sync function over the scope. Write them once, in `policies.ts`, as type guards:

```ts
// src/policies.ts
export type Actor = { id: string; role: "guest" | "agent" | "owner" | "admin" };
type Base = { accountId: string; locale: string };

export type SignedOutScope = Base & { actor: null };
export type MemberScope = Base & { actor: Actor };
export type StaffScope = Base & { actor: Actor & { role: "agent" | "owner" | "admin" } };
export type AdminScope = Base & { actor: Actor & { role: "admin" } };
// Signed in or not: a union, so guards can narrow it
export type Scope = SignedOutScope | MemberScope;

export const anyone = () => true;
export const member = (s: Scope): s is MemberScope => s.actor !== null;
export const staff = (s: Scope): s is StaffScope => s.actor !== null && s.actor.role !== "guest";
export const admin = (s: Scope): s is AdminScope => s.actor?.role === "admin";
```

Make `Scope` a union of signed in and signed out: then a simple check like `member` narrows it (TypeScript would even infer the guard). Compound checks like `staff` and `admin` look inside the actor, so they need their `s is ...` written out. Inside `handler`, `ctx.scope` has the narrowed type.

## `authorize`: who may call the function

```ts
/** Block dates on a property's calendar */
export const block = mutation({
  input: BlockInput,
  authorize: member,

  async handler(ctx, input) {
    // No null check: member guarantees an actor
    const blockedBy = ctx.scope.actor.id;
    ...
  },
});
```

- **Runs on every call**: from HTTP, from an agent, from another function, from your own job. Nested calls too.
- **Runs first**, before input validation, before any transaction opens.
- **Must return exactly `true`.** Anything else is `forbidden` (403), even when nobody is signed in, like Laravel.
- **Sync, and reads only the scope.** No database, no input. A policy that returns a Promise throws.

## Publishing: your routes, not a flag

A function is published by passing it to an adapter: your oRPC router, an AI tool, a route that calls it. That list is your API surface, in one file you review, like Rails' `routes.rb` or Laravel's `routes/api.php`:

```ts
// src/rpc.ts
export const router = {
  bookings: { cancel: toORPCProcedure(bookings.cancel), list: toORPCProcedure(bookings.list) },
};
```

The adapters need `authorize`: a published function says who may call it, and everyone is a decision too (`authorize: anyone`). Without one, `toORPCProcedure` and `toAITool` are a type error, and throw if a cast gets through. Add an [`output`](/docs/concepts/output) too: it decides what leaves.

Next.js, TanStack Start and Convex do the opposite: a server function is an endpoint by definition, and their docs tell you to check auth inside each one. Here nothing is reachable until you list it.

## Internal functions

A function no adapter publishes is internal: other functions `run` it, and your own server code (jobs, webhooks, scripts) calls it with `caller.run`. `authorize` is optional there, and still runs if you set it.

## Record rules: `can*`

`authorize` can't see the booking, so "only its creator or an admin may cancel it" goes in `handler`, after loading the record. Two steps:

1. **Load through an account-scoped helper.** It filters by `ctx.scope.accountId` and throws `notFound`, so another account's id is a 404, never a 403 that confirms it exists.
2. **Ask a sync predicate named `can*`.** `false` is `ctx.errors.deny()`, a 403.

```ts
// src/bookings/data.ts
export const canCancel = (actor: Actor, booking: BookingRow) =>
  actor.role === "admin" || booking.createdBy === actor.id;

// src/bookings/mutations.ts
async handler(ctx, input) {
  const booking = await findBooking(ctx, input.bookingId); // other accounts: 404
  if (!canCancel(ctx.scope.actor, booking)) throw ctx.errors.deny(); // 403
  ...
}
```

The same predicate feeds your UI, so the button and the rule never disagree:

```ts
/** List the account's bookings */
export const list = query({
  output: z.array(Booking.extend({ can: z.object({ cancel: z.boolean() }) })),
  authorize: member,

  async handler(ctx) {
    const rows = await listBookings(ctx);
    return rows.map((b) => ({ ...b, can: { cancel: canCancel(ctx.scope.actor, b) } }));
  },
});
```

This is how 37signals writes Fizzy. A controller says `before_action :ensure_permission_to_administer_card`, which does `head :forbidden unless Current.user.can_administer_card?(@card)`, and the predicate is a plain method:

```ruby
def can_administer_card?(card)
  admin? || card.creator == self
end
```

Laravel's policies are the same shape: boolean methods on a user and a record.

### What the CLI checks

| Rule | Catches |
|---|---|
| `async-can` | A `can*` predicate that's `async` or returns a Promise. Load first, then ask. |
| `unused-can` | A `can*` call whose result is thrown away, so nothing is enforced |

`logic-sdk show bookings.cancel` lists the predicates a function calls under `checks:`, next to its policy.

## Nested calls and listeners

- **Nested calls keep the scope**, and each callee's `authorize` runs against it.
- **Listeners run with the emitter's scope.** A booking confirmed by a guest reaches `tasks.prepareStay` as that guest.
- So **listeners and jobs run internal functions**, which carry no `authorize` or one that fits the job. Keep published functions thin: check, then `run` the internal function that does the work.
- **Acting as someone else on purpose** is a scope change for one call, and every check inside it sees the new one. `logic-sdk show` lists it on that run: `tasks.create (scope: actor)`.

```ts
const system = { id: "system", role: "admin" } as const;

await ctx.run(tasks.create, { bookingId, title: "Prepare the house" }, { scope: { actor: system } });
```

## Recipes

**A rule that must hold at commit**, not just when you checked, goes into the write itself. Put it in the `WHERE`:

```ts
const [updated] = await ctx.db
  .update(bookings)
  .set({ status: "cancelled" })
  .where(and(eq(bookings.id, booking.id), eq(bookings.status, "pending")))
  .returning();

if (!updated) throw ctx.errors.conflict("no_longer_pending");
```

Or re-select the row `FOR UPDATE`, so concurrent writers wait, then check:

```ts
const [row] = await ctx.db
  .select()
  .from(bookings)
  .where(and(eq(bookings.accountId, ctx.scope.accountId), eq(bookings.id, bookingId)))
  .for("update");
```

**Tenancy is yours.** The library guarantees the scope reaches every function and helper. Filtering by `ctx.scope.accountId`, reads and writes, is your helpers' job.

## How other stacks do it

| Stack | What it does |
|---|---|
| Rails (Fizzy) | `before_action` calls `Current.user.can_administer_card?(@card)` and answers `head :forbidden` |
| Laravel | Policies are boolean methods on (user, record). A failed policy is a 403, signed in or not |
| Phoenix 1.8 | Scopes: an explicit scope, secure by default, passed by hand to every function. Here it's bound once |
| Next.js | Recommends a Data Access Layer that checks who's calling. This is that layer, as a library |
| Convex | Functions are public unless `internal*`. Here they're internal unless an adapter publishes them |

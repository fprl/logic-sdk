title: Errors
description: Six kinds, codes namespaced to your module, and when catching makes sense.
---

Throw expected failures from `ctx.errors`. The code gets your module's name for you:

```ts
// Inside bookings.cancel

// A rule said no, and trying again won't help: "bookings.not_pending"
throw ctx.errors.reject("not_pending", { status });

// Someone got there first, or it already exists: "bookings.dates_taken"
throw ctx.errors.conflict("dates_taken");

// It doesn't exist, or isn't visible here: "bookings.not_found"
throw ctx.errors.notFound();

// The caller may not do this: "bookings.cancel.forbidden"
throw ctx.errors.deny();
```

Every expected failure is a `DomainError` with a `kind`, a `code` and optional `details`.

**Why `throw` and not a method that throws?** TypeScript narrows after `throw`: below `if (!booking) throw ...`, `booking` is defined. A `never`-returning method would only narrow if its type were declared explicitly, and `ctx` is contextually typed, so it wouldn't.

## Kinds

| Kind | Means | Thrown by |
|---|---|---|
| `invalid` | The input doesn't match the schema | The library |
| `unauthenticated` | There's no valid session | Your edge: `unauthenticated()` from `logic-sdk` |
| `forbidden` | The caller may not do this | The library when `authorize` fails, or `ctx.errors.deny()` |
| `not_found` | It doesn't exist here | `ctx.errors.notFound()` |
| `conflict` | Someone got there first | `ctx.errors.conflict(code)` |
| `rejected` | A rule said no | `ctx.errors.reject(code)` |

Kinds are domain words, not status codes. Each adapter maps them: see [HTTP](/docs/adapters/fetch#errors) and [oRPC](/docs/adapters/orpc#errors).

## Unexpected errors

Anything else that's thrown is a bug: a plain `Error`, invalid output, an invalid event payload. Clients get a generic 500 `internal` without details, and the error goes to `onError`. Unexpected errors aren't part of a function's contract.

Bad input works the same way. From a client, it's `invalid` (400). From a nested `ctx.run`, it's your own code passing the wrong thing: a bug, so a 500.

## Authentication lives at the edge

Whether there's a valid session is decided before any function runs, in the code that builds the scope. Two cases:

- **The mount serves public functions too:** return a scope with no actor. Functions that need one fail their policy with `forbidden` (403).
- **The mount is entirely session-only** (an admin API, say): throw `unauthenticated()` where you build the scope, and `toResponse` makes it a 401.

```ts
import { unauthenticated } from "logic-sdk";

async function callerFor(request: Request) {
  const session = await auth.getSession(request);
  if (!session) throw unauthenticated();
  return registry.as(scopeFrom(session));
}
```

With oRPC, throw `ORPCError("UNAUTHORIZED")` from your own middleware instead. Inside modules there's no 401: a caller who may not do something gets `forbidden`.

## Whose code is it?

A module only creates codes in its own namespace. Another module's error passes through `run` unchanged:

```ts
// bookings.confirm runs availability.hold, which throws.
// The caller sees availability's code, untouched:
// "availability.dates_unavailable"
await caller.run(bookings.confirm, { bookingId });
```

## Why codes aren't typed

The six kinds are a fixed, typed set. Codes are plain strings, on purpose.

Functions call each other. The honest list of codes `bookings.confirm` can fail with includes every code from every function it runs, and a typed list per function would have to repeat them all to stay true.

Test the codes that matter, and branch on one with `isDomainError`:

```ts
if (isDomainError(error, "bookings.not_pending")) {
  // ...
}
```

## Catching

Errors bubble up to the edge by default, and most code never catches them. When you do, where you catch decides what you can do.

**In an action, catch and recover.** Each mutation the action ran committed (or failed) on its own.

```ts
try {
  await ctx.run(bookings.confirm, { bookingId });
} catch (error) {
  if (isDomainError(error, "availability.dates_unavailable")) {
    return suggestOtherDates();
  }
  throw error;
}
```

**In a mutation, catch only to translate.** The transaction is already doomed and will roll back.

```ts
try {
  await ctx.run(availability.hold, range);
} catch {
  throw ctx.errors.reject("cannot_confirm");
}
```

Postgres itself aborts a transaction after a failed statement, so nothing after the catch can write.

## Database errors

Map the database errors you care about where you know what they mean. `sqlState` reads the SQLSTATE code, even when Drizzle wraps the error:

```ts
import { sqlState } from "logic-sdk/drizzle/pg";

try {
  await ctx.db.insert(users).values(input);
} catch (error) {
  // unique_violation
  if (sqlState(error) === "23505") throw ctx.errors.conflict("email_taken");
  throw error;
}
```

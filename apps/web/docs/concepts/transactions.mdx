## One transaction per mutation

A top-level mutation opens a transaction. Every mutation it runs joins that same transaction, across modules:

```ts
async handler(ctx, input) {
  const booking = await findBooking(ctx, input.bookingId);

  // Joins this transaction
  await ctx.run(availability.hold, rangeOf(booking));

  // If this throws, the hold above rolls back too
  return setStatus(ctx, booking.id, "confirmed");
}
```

The policy is checked and the input validated **before** the transaction opens, so bad or denied calls never take a database connection.

## A failure rolls back everything

If a nested mutation throws, the whole transaction is doomed, even if the caller catches the error. Partial writes can't commit.

```ts
try {
  await ctx.run(availability.hold, range);
} catch {
  // The transaction is already doomed: this write rolls back too
  await ctx.run(notes.add, { text: "hold failed" });
}
```

Postgres does the same after a failed statement, and so does Ecto: a rescued inner failure aborts [the whole outer transaction](https://github.com/elixir-ecto/ecto/blob/master/lib/ecto/repo.ex). See [catching errors](/docs/concepts/errors#catching) for what you can do instead.

When the caller caught the failure and returned, the commit fails with an error of its own. It names the path down to the failure, and keeps the failure as its `cause`:

```text
[logic-sdk] reminders.wake failed inside reminders.wakeDue's transaction (reminders.wakeDue → reminders.wake)
and was caught, so reminders.wakeDue can't commit: a mutation shares its transaction with the mutations it runs.
To let each one commit or fail on its own, run them from an action. The failure (this error's cause): …
```

A job is retried the way its cause would be, so a swallowed `reject` still fails at once.

## One commit per item

Where the transaction ends depends on who calls. A mutation's nested mutations join its transaction. An action has none, so each mutation it runs commits on its own:

| Caller | `ctx.run(mutation)` | One fails and is caught |
| --- | --- | --- |
| `mutation` | joins the caller's transaction | nothing commits |
| `action`, listener, cron | its own transaction | the others commit |

Work over many rows where each must succeed or fail alone, like a cron over every account, runs from a cron's handler (or an action):

```ts
/** Every minute: wake each due reminder in its own transaction */
export const wakeDue = cron({
  schedule: "* * * * *",
  scope: asSystem("reminders.wakeDue"),
  async handler(ctx) {
    for (const { id } of await ctx.run(dueReminders)) {
      try {
        await ctx.run(wake, { reminderId: id });
      } catch (error) {
        console.error(error); // one bad row doesn't block the rest
      }
    }
  },
});
```

Written as a mutation, one bad row would roll back every other row's work, every time it runs. Convex draws the same line: an action's [`runMutation` calls run in separate transactions](https://github.com/get-convex/convex-backend/blob/main/npm-packages/docs/docs/functions/actions.mdx).

## Lost races are retried

Sometimes Postgres aborts a transaction because it lost a race with another one: a deadlock (`40P01`) or a serialization failure (`40001`). The registry then runs the whole mutation again, in a fresh transaction.

- Up to **3 attempts**, with a short random pause between them.
- **Even when a caller caught it.** A nested mutation that lost the race dooms the transaction, so the whole mutation runs again, even if its caller went on and Postgres then failed the next statement (`25P02`).
- **Safe**, because mutations have no side effects and their events are rebuilt on each attempt.
- **Familiar**: Laravel does the same with `DB::transaction(fn, attempts)`, and Convex re-runs conflicting mutations automatically.
- **Not a job retry**: a listener's `attempts` decide how often a job runs. Each of those runs can retry its own transactions.

It's a database setting, so it goes on the database adapter:

```ts
createRegistry({
  modules,
  // 1 turns retries off
  database: drizzleAdapter(db, { transactionAttempts: 5 }),
});
```

With your own adapter, set `transactionAttempts` next to `retryable`.

## Lock rows in one order

Two transactions that lock the same rows in opposite orders deadlock, and retries only make that rarer. Write them in one order, by key:

```ts
const items = input.items.toSorted((a, b) => (a.sku < b.sku ? -1 : 1));
for (const item of items) await takeStock(ctx, item);
```

## Retries don't replace locks

When a rule depends on rows that don't exist yet, like "no two bookings overlap", two transactions can both pass the check. Lock first, then check:

```ts
/** Reserve a date range on a property's calendar */
export const hold = mutation({
  input: HoldInput,

  async handler(ctx, input) {
    // One hold at a time per property. A concurrent confirm waits here,
    // then sees the committed hold in the check below.
    await ctx.db.execute(
      sql`select pg_advisory_xact_lock(hashtext(${input.propertyId}))`,
    );

    const clashes = await overlapping(ctx, input);
    if (clashes.length) throw ctx.errors.conflict("dates_unavailable");

    const [hold] = await ctx.db.insert(holds).values(input).returning();
    return hold;
  },
});
```

The `examples/bookings` app races three agents confirming overlapping dates on real Postgres: one wins, and the others get a clean `conflict`.

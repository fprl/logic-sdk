## One transaction per mutation

A top-level mutation opens a transaction. Every mutation it runs joins that same transaction, across modules:

```ts
async handler(ctx, input) {
  const booking = await findBooking(ctx, input.bookingId);

  // Joins this transaction
  await ctx.run(availability.hold, rangeOf(booking));

  // If this throws, the hold above rolls back too
  return setStatus(ctx, booking.id, "confirmed");
}
```

The policy is checked and the input validated **before** the transaction opens, so bad or denied calls never take a database connection.

## A failure rolls back everything

If a nested mutation throws, the whole transaction is doomed, even if the caller catches the error. Partial writes can't commit.

```ts
try {
  await ctx.run(availability.hold, range);
} catch {
  // The transaction is already doomed: this write rolls back too
  await ctx.run(notes.add, { text: "hold failed" });
}
```

Postgres does the same after a failed statement. See [catching errors](/docs/concepts/errors#catching) for what you can do instead.

## Lost races

Sometimes Postgres aborts a transaction because it lost a race with another one: a deadlock (`40P01`) or a serialization failure (`40001`). By default that error reaches the caller, as in Laravel. Set `transactionAttempts` and the registry runs the whole mutation again, in a fresh transaction, after a short random pause.

- **Default 1**: no retry, like Laravel's `DB::transaction`.
- **Safe**, because mutations have no side effects and their events are rebuilt on each attempt.
- **Not a job retry**: a listener's `attempts` decide how often a job runs. Each of those runs can retry its own transactions.

It's a database setting, so it goes on the database adapter:

```ts
createRegistry({
  modules,
  database: drizzleAdapter(db, { transactionAttempts: 3 }),
});
```

With your own adapter, set `transactionAttempts` next to `retryable`.

## Lock rows in one order

Two transactions that lock the same rows in opposite orders deadlock. Write them in one order, by key:

```ts
const items = input.items.toSorted((a, b) => (a.sku < b.sku ? -1 : 1));
for (const item of items) await takeStock(ctx, item);
```

## Retries don't replace locks

When a rule depends on rows that don't exist yet, like "no two bookings overlap", two transactions can both pass the check. Lock first, then check:

```ts
/** Reserve a date range on a property's calendar */
export const hold = mutation({
  input: HoldInput,

  async handler(ctx, input) {
    // One hold at a time per property. A concurrent confirm waits here,
    // then sees the committed hold in the check below.
    await ctx.db.execute(
      sql`select pg_advisory_xact_lock(hashtext(${input.propertyId}))`,
    );

    const clashes = await overlapping(ctx, input);
    if (clashes.length) throw ctx.errors.conflict("dates_unavailable");

    const [hold] = await ctx.db.insert(holds).values(input).returning();
    return hold;
  },
});
```

The `examples/bookings` app races three agents confirming overlapping dates on real Postgres: one wins, and the others get a clean `conflict`.

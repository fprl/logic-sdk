title: Functions and ctx
description: Queries, mutations, actions and listeners, and what each one gets in ctx.

Every function is a plain object with a description, an input schema and an `execute`. The kind decides what `execute` may touch.

```ts
export const priceStay = query({
  description: "Price a stay: nights × rate + cleaning fee",
  inputSchema: z.object({
    propertyId: z.uuid(),
    from: z.iso.date(),
    to: z.iso.date(),
  }),

  async execute({ propertyId, from, to }, ctx) {
    const property = await ctx.run(properties.get, { propertyId });
    const nights = nightsBetween(from, to);
    return { nights, total: nights * property.nightlyRate };
  },
});
```

- **`query`** reads. It can run other queries.
- **`mutation`** writes, inside one transaction. It can run queries and mutations, and emit events.
- **`action`** talks to the outside world: payments, email, AI. It has no transaction, so each mutation it runs commits on its own.
- **`on(() => event, fn)`** reacts to an event after commit. It behaves like an action.

The `description` is one sentence. People read it, and so do adapters and AI tools.

## ctx

The second argument of `execute`:

| | query | mutation | action and listener |
|---|---|---|---|
| `scope` | ✓ | ✓ | ✓ |
| `db` | read-only | the transaction | |
| `run(fn, input)` | queries | queries and mutations | anything |
| `emit(event, payload)` | | ✓ | |
| `services` | | | ✓ |
| `now()` | ✓ | ✓ | ✓ |
| `with(patch)` | ✓ | ✓ | ✓ |
| `reject`, `conflict`, `notFound`, `deny` | ✓ | ✓ | ✓ |
| `signal` | ✓ | ✓ | actions only |
| `event` | | | listeners only |

Time comes from `ctx.now()`, never `new Date()`, so tests can freeze it.

## Helpers take ctx

Shared logic lives in plain functions that take the whole `ctx`, the way Convex recommends. They read `ctx.db` and `ctx.scope`, so tenancy filters can't be forgotten.

```ts
export async function findBooking(ctx: QueryCtx, id: string) {
  const [booking] = await ctx.db
    .select()
    .from(bookings)
    .where(
      and(
        eq(bookings.accountId, ctx.scope.accountId),
        eq(bookings.id, id),
      ),
    );

  if (!booking) throw ctx.notFound();
  return booking;
}
```

A mutation's `ctx` works wherever a `QueryCtx` is expected, so one read helper serves both.

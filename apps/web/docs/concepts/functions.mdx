title: Functions and ctx
description: Queries, mutations, actions and listeners, and what each one gets in ctx.
---

Every function is a plain object with an `input` schema and a `handler(ctx, input)`, with a JSDoc comment above it. The kind decides what `handler` may touch.

```ts
/** Price a stay: nights × rate + cleaning fee */
export const priceStay = query({
  input: z.object({
    propertyId: z.uuid(),
    from: z.iso.date(),
    to: z.iso.date(),
  }),

  async handler(ctx, input) {
    const { propertyId, from, to } = input;
    const property = await ctx.run(properties.get, { propertyId });
    const nights = nightsBetween(from, to);
    return { nights, total: nights * property.nightlyRate };
  },
});
```

- **`query`** reads. It can run other queries.
- **`mutation`** writes, inside one transaction. It can run queries and mutations, and emit events.
- **`action`** talks to the outside world: payments, email, AI. It has no transaction, so each mutation it runs commits on its own.
- **`listener({ event: () => ev, handler(ctx, payload) })`** reacts to an event after commit. It behaves like an action.

The JSDoc above it is one sentence. Your editor shows it on hover wherever the function is used, and `logic-sdk list` and `show` print it. What an AI tool reads lives in [meta](/docs/concepts/meta), owned by the adapter: `meta: { ai: { description } }`.

A function that takes nothing leaves out `input`. Its handler gets only `ctx`, and callers write `run(fn)`:

```ts
/** Everything for sale */
export const list = query({
  handler: (ctx) => ctx.db.select().from(products),
});

await caller.run(catalog.list);
```

A function keeps its schema as you wrote it, so a form can take its fields from the function it calls instead of a schema you export:

```ts
const fields = properties.update.input.pick({ name: true, city: true });
```

Without `input`, `fn.input` is `undefined`.

`ctx` comes first everywhere: in handlers, in listeners (`handler(ctx, payload)`) and in your own helpers.

## ctx

The first argument of `handler`:

| | query | mutation | action and listener |
|---|---|---|---|
| `scope` | ✓ | ✓ | ✓ |
| `db` | read-only | the transaction | |
| `run(fn, input, { scope?, signal? })` | queries | queries and mutations | anything |
| `emit(event, payload)` | | ✓ | |
| `services` | | | ✓ |
| `now()` | ✓ | ✓ | ✓ |
| `errors` (`reject`, `conflict`, `notFound`, `deny`) | ✓ | ✓ | ✓ |
| `config` | ✓ | ✓ | ✓ |
| `signal` | | | ✓ (undefined in listeners) |
| `event` | | | listeners only |

Time comes from `ctx.now()`, never `new Date()`, so tests can freeze it.

## Helpers take ctx

Shared logic lives in plain functions that take the whole `ctx`. They read `ctx.db` and `ctx.scope`, so tenancy filters can't be forgotten.

```ts
export async function findBooking(ctx: QueryCtx, id: string) {
  const [booking] = await ctx.db
    .select()
    .from(bookings)
    .where(
      and(
        eq(bookings.accountId, ctx.scope.accountId),
        eq(bookings.id, id),
      ),
    );

  if (!booking) throw ctx.errors.notFound();
  return booking;
}
```

A mutation's `ctx` works wherever a `QueryCtx` is expected, so one read helper serves both.

## Helper or `run`?

Inside a module, you can call your own functions two ways. They aren't the same:

| | `ctx.run(fn, input)` | A helper in `data.ts` |
|---|---|---|
| The callee's `authorize` | Runs (a fast, sync check on the scope, no database) | No |
| Input validation, output parsing | Yes | No |
| Traced by `wrap` | Yes | No |
| What it is | A call through the registry | Plain TypeScript |

**Within a module, prefer helpers.** Use `run` on your own module's function when you want its policy and validation, for example to reuse a mutation whose rules you'd otherwise copy.

**Across modules, always `run`**, through the other module's index. Never import its `data.ts` or `schema.ts`.

## Private functions

A function its module's index doesn't export is private: only that module's own code can reach it, and `ctx.run` runs it as part of the module that runs it. You need one when an action has to write. An action has no `db`, so the write is a mutation, and exported, any module, route or agent could call it directly and skip what the action checks first.

```ts
// files/actions.ts
/** Record a stored file */
const record = mutation({            // no export: nothing outside this file can reach it
  input: fileInsertSchema.pick({ key: true, contentType: true, byteSize: true }),
  authorize: member,
  async handler(ctx, input) { /* insert */ },
});

/** Record an upload once its first bytes show the type the browser claimed */
export const upload = action({
  // ...
  async handler(ctx, input) {
    const head = await ctx.services.storage.download(input.key, { range: { start: 0, end: 511 } });
    if (detectContentType(new Uint8Array(await head.arrayBuffer())) !== input.contentType) throw ctx.errors.reject("mismatch");
    return ctx.run(record, input);
  },
});
```

| | Exported from the index | Private |
|---|---|---|
| `ctx.run` | Runs as its own module | Runs as the module that runs it: `files.(private)` in `wrap`, `files.<id>` if it sets `id` |
| `ctx.schedule`, a cron's `run`, `registry.as(scope).run`, adapters, tests' `t.run` | Yes | Refused: they find code by name, and a private one has none |

When two files of the module need the same private function, put it in `data.ts` and import it from there: the index never re-exports `data.ts`. Not in `mutations.ts`: exporting it from there for the other file would make the index's `export * from "./mutations"` publish it.

Test a private function through the exported one that runs it, as with any unexported code. Another module importing `files/data.ts` directly would run it as its own: keep imports to each module's index with your linter (`logic-sdk graph` shows the edge). A listener, cron or event the index doesn't export never runs.

**Reads go both ways, writes go one way.** A properties page can `run` a bookings query while creating a booking `run`s a properties query: a query can't write, emit or schedule, so that's not a cycle. Don't have modules run each other's mutations or actions in a circle: make one direction an event.

**`ctx.run` nests at most 64 calls deep.** Past that it throws a plain error with the path (`… → a.ping → b.pong → a.ping`), because a function that runs itself, directly or through other modules, never returns. Recurse in a helper that takes `ctx` instead, or make each step separate work: an event, or `ctx.schedule`.

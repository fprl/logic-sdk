```ts
// orders/crons.ts
export const morningDigest = cron({
  schedule: "0 8 * * 1-5",     // weekdays at 8:00
  timezone: "Europe/Madrid",   // optional, default UTC
  run: sendDigest,             // any query, mutation or action
  scope: system,               // who it runs as: a cron has no caller
});
```

- **One cron per export,** found through your modules like listeners, so a new one can't be forgotten.
- **`run` is a normal function:** it keeps its `authorize`, validation and tracing, and you call it from anywhere else too. `input` is what it gets, typed by it and required when it needs one: `input: { kind: "weekly" }`.
- **`scope` is required:** policies and data helpers read `ctx.scope`, and a cron has no caller to take it from.
- **`attempts`** works like a listener's: default 1.

## Ticking

Your crons live in code. Something calls `registry.jobs.tick()`, which runs every cron due in that minute:

**Node:**

```ts
// on the minute, so no minute is skipped or ticked twice
const tickEveryMinute = () => {
  setTimeout(async () => {
    await registry.jobs.tick();
    await registry.jobs.sweep(); // with the outbox
    tickEveryMinute();
  }, 60_000 - (Date.now() % 60_000));
};
tickEveryMinute();
```

**Cloudflare:** one trigger per cron (the same strings), or `"* * * * *"` for all of them:

```jsonc
// wrangler.jsonc
{ "triggers": { "crons": ["0 9 * * 1", "0 18 * * 5"] } }
```

```ts
async scheduled(controller, env, ctx) {
  await handleScheduled(makeRegistry(env, ctx), controller); // tick at the trigger's time, then sweep
}
```

**Vercel:** a schedule per cron, or one every minute, all calling the same route:

```json
{
  "schedules": {
    "weekly-report": { "schedule": "0 9 * * 1", "path": "/api/tick" },
    "friday-digest": { "schedule": "0 18 * * 5", "path": "/api/tick" }
  }
}
```

```ts
// app/api/tick/route.ts
export async function POST(request: Request) {
  if (request.headers.get("authorization") !== `Bearer ${process.env.CRON_SECRET}`) {
    return new Response("Unauthorized", { status: 401 });
  }
  const at = request.headers.get("ce-vssscheduledat"); // the scheduled time, without jitter
  await registry.jobs.tick(at ? new Date(at) : undefined);
  await registry.jobs.sweep();
  return new Response(null, { status: 204 });
}
```

- **A trigger only says when to tick;** `tick` matches the time, not which trigger fired. So one trigger per cron and one every minute both work.
- **Every minute never needs touching,** and it's Laravel's setup: one system cron entry, `* * * * * php artisan schedule:run`. It costs about 43,000 calls a month: nothing on Cloudflare's paid plan, cents on Vercel Pro.
- **One trigger per cron calls less,** but keep the lists in step: a cron with no trigger never runs, and nothing can tell you, since logic-sdk doesn't read `wrangler.jsonc` or `vercel.json`.
- **The platform's own limits apply:** Cloudflare's crons are UTC, so a cron with a `timezone` needs a trigger that covers it (every minute, or every hour for one on the hour). Vercel Hobby fires at most every 15 minutes.
- **pg-boss** (planned) needs no triggers: the adapter schedules each cron in pg-boss from your code.

## Once, on several servers

Each tick is a job with the id `<cron id>@<minute>`, through your [jobs adapter](/docs/concepts/jobs):

- **With `outbox(db)`, a minute runs once,** however many servers tick it, and a trigger delivered twice runs once too. Re-export the runs table next to the outbox's, like Solid Queue's recurring executions:

```ts
// db/schema.ts
export { outboxTable, cronRunsTable } from "logic-sdk/drizzle";
```

- **With `inProcess()`, every server that ticks runs it,** like Laravel without `onOneServer()`. Fine for one server, or for a platform trigger; use the outbox for more.
- **Failures** are the same as a listener's: retried while `attempts` are left, kept as `failed` rows by the outbox, reported to `onError` with the cron's id.

## Schedules

Five fields, `minute hour day-of-month month day-of-week`: lists, ranges and steps (`1,15`, `9-17`, `*/5`, `1-30/5`), names (`JAN`, `MON`) and `7` for Sunday. When both day fields are set (`0 0 13 * 5`), either one matching is enough, like classic cron.

- **Not supported:** seconds, `@daily`-style aliases, and `L`, `W`, `#`. `createRegistry` fails with what to write instead.
- **Time zones:** an IANA name, matched on the clock there. Like Laravel, a time skipped when clocks go forward doesn't run that day, and one that happens twice when they go back runs twice. Avoid 1:00 to 3:00 in a time zone with DST, or use UTC.
- **A tick runs what's due now.** A minute nobody ticked (the server was down) is skipped, not caught up, like pg-boss's default. Runs may overlap, like Laravel, Oban and Vercel.

## Testing

```ts
test("weekday mornings, staff get a digest", async () => {
  await t.jobs.tick("2026-12-01T07:00:00Z"); // 8:00 in Madrid, a Tuesday
  expect(mailer.sent).toHaveLength(1);
});
```

`t.jobs.tick(at)` runs the crons due at that minute, here and now, and throws a failure. Without `at` it uses the test's `now`. To test what a cron does, run its function: `t.as(system).run(sendDigest)`.

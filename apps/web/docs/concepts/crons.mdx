```ts
// orders/crons.ts
/** Weekday mornings, email staff how many orders wait to ship */
export const sendDigest = cron({
  schedule: "0 8 * * 1-5",                 // weekdays at 8:00
  timezone: "Europe/Madrid",               // optional, default UTC
  scope: { kind: "system", job: "orders.sendDigest" }, // who it runs as: your scope, a cron has no caller
  async handler(ctx) {
    const waiting = await ctx.run(toShip); // checks toShip's policy against that scope
    if (waiting > 0) await ctx.services.mailer.send({ to: "staff", subject: `${waiting} orders to ship` });
  },
});
```

- **A listener reacts to an event, a cron to the clock.** Same shape: a `handler` with an action's ctx, exported from its module and found like listeners, so a new one can't be forgotten.
- **Named after its work,** like a listener: `sendDigest`, not `morningDigest`. A cron that runs shared work (a function something else also calls) is named for when it runs: `export const nightly = cron({ …, handler: (ctx) => ctx.run(reports.rebuild) })`.
- **What it runs checks its policy.** Every `ctx.run` checks the function's `authorize` against the cron's scope, as in a listener, so the work keeps its policy, validation and tracing.
- **`scope` is required:** policies and data helpers read `ctx.scope`, and a cron has no caller to take it from. Use a [system scope](/docs/concepts/scope#the-system), a variant of your own `Scope` like `{ kind: "system", job: "orders.sendDigest" }`, not a fake user, and grant it in policies (`staffOrSystem`). In the handler, `ctx.scope` is typed as the scope you declared.
- **`ctx.cron`** says which run this is: `id`, `scheduledAt` (the minute it's for, even when it runs late or again: which day a digest covers) and `attempt`.
- **`attempts`** works like a listener's: default 1. A retry runs the whole handler again, so make it idempotent, like a listener. Work that must be all or nothing goes in one `ctx.run(mutation)`; each mutation it runs commits on its own, so a `try`/`catch` per row lets one row fail without the rest.
- **`meta`** works like a listener's: `wrap` and plugins see the run as `kind: "cron"`, and pg-boss reads `meta.pgBoss`.
- **Its `scope` comes from your code each time it runs,** never stored, so `jobs.scope.store` and `load` don't apply to the cron itself, and a deploy that changes it applies to runs already queued. What it emits or schedules is stored as usual, so a [system scope](/docs/concepts/scope#the-system) must survive your `store` and `load`.

## Ticking

Your crons live in code. Something calls `registry.jobs.tick()`, which runs every cron due in that minute:

**Node:** a long-running process is its own trigger, like Laravel's `schedule:work`:

```ts
import { startTicking } from "logic-sdk/node";

const stop = startTicking(registry); // ticks every minute, sweeps every 60 s: { sweepEvery }
process.on("SIGTERM", async () => {
  await stop(); // waits for the running ticks and sweep, 30 s at most: { timeout }
  process.exit(0);
});
```

- **It ticks on the minute and sweeps every `sweepEvery` seconds, without waiting for the last,** so a slow cron or a hung job doesn't hold back the rest. Ten of either still running means something's stuck: the next is skipped and reported to `onError`.
- **Ticks don't pile up:** with ten still running (stuck on an unreachable database, or ten slow crons overlapping), the next minute is skipped and reported to `onError`, so a backlog of stale minutes doesn't all run when the database comes back.

**Cloudflare:** `"* * * * *"` for all of them, or one trigger per cron. Cloudflare numbers weekdays 1 = Sunday (we use classic cron's 1 = Monday), so write weekdays as names, in your code and in the trigger:

```jsonc
// wrangler.jsonc
{ "triggers": { "crons": ["0 9 * * MON", "0 18 * * FRI"] } }
```

```ts
async scheduled(controller, env, ctx) {
  await handleScheduled(makeRegistry(env, ctx), controller); // tick at the trigger's time, then sweep
}
```

**Vercel:** a schedule per cron, or one every minute, all calling the same route:

```json
{
  "schedules": {
    "weekly-report": { "schedule": "0 9 * * 1", "path": "/api/tick" },
    "friday-digest": { "schedule": "0 18 * * 5", "path": "/api/tick" }
  }
}
```

```ts
// app/api/tick/route.ts
export async function POST(request: Request) {
  const secret = process.env.CRON_SECRET;
  // without the first check, an unset secret would let `Bearer undefined` in
  if (!secret || request.headers.get("authorization") !== `Bearer ${secret}`) {
    return new Response("Unauthorized", { status: 401 });
  }
  const at = request.headers.get("ce-vssscheduledat"); // the scheduled time, without jitter
  await registry.jobs.tick(at ? new Date(at) : undefined);
  await registry.jobs.sweep();
  return new Response(null, { status: 204 });
}
```

- **A trigger only says when to tick;** `tick` matches the time, not which trigger fired. So one trigger per cron and one every minute both work.
- **With `databaseQueue`, you need a regular trigger anyway:** the request runs a commit's jobs itself, but retries, delayed jobs and what a crash left behind wait for a sweep, and the trigger's interval is how long they wait. That trigger ticks your crons too, so per-cron triggers only make sense without it, where a trigger delivered twice runs the cron twice.
- **Every minute never needs touching,** and it's Laravel's setup: one system cron entry, `* * * * * php artisan schedule:run`. It costs about 43,000 calls a month: nothing on Cloudflare's paid plan, cents on Vercel Pro.
- **One trigger per cron calls less,** but keep the lists in step: a cron with no trigger never runs, and nothing can tell you, since logic-sdk doesn't read `wrangler.jsonc` or `vercel.json`.
- **The platform's own limits apply:**
  - Cloudflare's triggers are UTC, so a cron with a `timezone` needs a trigger that covers it: every minute, or every hour when its time falls on the hour in UTC too (Madrid yes, India's half-hour offset no).
  - Vercel refuses names in its schedules, and a day-of-month together with a day-of-week, so copy those crons as numbers or use one every-minute schedule. Vercel Hobby fires at most every 15 minutes.
- **pg-boss** needs no trigger: `work(registry, boss)` ticks your crons every minute in each worker process. See [pg-boss](/docs/adapters/pg-boss).

## Once, on several servers

**`databaseQueue`, `outbox` and pg-boss run a cron once when several servers tick it.** With `inProcess()`, each server runs it. `cloudflareQueue` alone runs it once per tick: a trigger delivered twice runs it twice.

Each tick is a job with the id `<cron id>@<minute>`, through your [jobs adapter](/docs/concepts/jobs):

- **With `databaseQueue` or `outbox`, a minute runs once,** however many servers tick it, and a trigger delivered twice runs once too. Re-export the runs table next to the jobs table, like Solid Queue's recurring executions:

```ts
// db/schema.ts
export { jobsTable, cronRunsTable } from "logic-sdk/drizzle/pg";
```

- **With `pgBoss(boss)`, a minute runs once** too: its pg-boss id is derived from `<cron id>@<minute>`, and pg-boss skips an insert whose id it already has (finished jobs are kept 7 days).
- **With `inProcess()`, every server that ticks runs it,** like Laravel without `onOneServer()`. Fine for one server, or for a platform trigger; use `databaseQueue` for more.
- **Failures** are the same as a listener's: retried while `attempts` are left, kept as `failed` by `databaseQueue`, `outbox`, pg-boss or a `failedJobs` store, reported to `onError` with the cron's id.

## Schedules

Five fields, `minute hour day-of-month month day-of-week`: lists, ranges and steps (`1,15`, `9-17`, `*/5`, `1-30/5`), names (`JAN`, `MON`) and `7` for Sunday. When both day fields are set (`0 0 13 * 5`), either one matching is enough, like classic cron.

- **Not supported:** seconds, `@daily`-style aliases, and `L`, `W`, `#`. `createRegistry` fails with what to write instead.
- **Time zones:** an IANA name, matched on the clock there. Like Laravel, a time skipped when clocks go forward doesn't run that day, and one that happens twice when they go back runs twice. Avoid 1:00 to 3:00 in a time zone with DST, or use UTC.
- **A tick runs what's due now.** A minute nobody ticked (the server was down, a deploy) is skipped, not caught up, like Laravel and pg-boss's default (`missed: 'skip'`). Rerun one with `invoke` (below). Runs may overlap, like Laravel, Oban and Vercel.

## Running one now

```ts
await registry.jobs.invoke(orders.sendDigest);                                          // now, from a staff button
await registry.jobs.invoke("orders.sendDigest", { at: new Date("2026-11-24T07:00Z") }); // a minute a deploy missed, from a script
```

- **Through your jobs adapter, like a tick,** with the cron's scope and `attempts`: Vercel's `Schedules.invoke`, Mission Control's "Run now" (`task.enqueue`), Oban Web's "Run Now". Its schedule and the next tick don't change.
- **Its own job id,** `orders.sendDigest@20261124T0700Z-<uuid>`, so the real tick for that minute still runs, and so does a second invoke. It resolves the id; a failure is kept under it, for `failed`, `retry` and `forget` ([Jobs](/docs/concepts/jobs#failed-jobs-and-running-a-cron-now)).
- **`at` is the minute the run is for,** what the handler reads as `ctx.cron.scheduledAt`. Default now. It isn't checked against the schedule.
- **The cron, or its id** from a script: an id that isn't registered throws, naming the ones that are.
- **Unlike a tick, it throws when the hand-off fails** (a queue that's down), so whoever pressed the button sees it.
- **Outside your functions:** guard the route that calls it, like any operator action.

## Testing

```ts
test("weekday mornings, staff get a digest", async () => {
  await t.jobs.tick("2026-12-01T07:00:00Z"); // 8:00 in Madrid, a Tuesday
  expect(mailer.sent).toHaveLength(1);
});
```

`t.jobs.tick(at)` runs the crons due at that minute, here and now, and throws a failure. Without `at` it uses the test's `now`. To run one cron, due or not, use `t.jobs.perform(orders.sendDigest, { at })`: it runs as the cron's own scope, for that minute.

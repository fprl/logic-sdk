---
title: CLI
description: List, inspect and graph your app from the terminal, for people and agents.
---

```bash
npm i -D @logic-sdk/cli
npx logic-sdk list
```

Run it from your app's root. The `logic-sdk` command comes with the main package and hands off to `@logic-sdk/cli`, so apps that don't use the CLI never download its parser.

Every command reads your code; none of them touch the database.

## list

Every function and listener, like a route list:

```txt
$ logic-sdk list
NAME                  KIND       POLICY   DESCRIPTION
bookings.confirm      mutation   staff    Confirm a pending booking: holds its dates…
bookings.checkout     action     anyone   Charge the guest and confirm the booking…
availability.hold     mutation   none     Reserve a date range on a property's calendar
tasks.prepareStay     listener   -        Create the key-handover task and email the gu…
```

POLICY is the `authorize` policy as written (`inline` for an arrow), or `none`. What's published is in your router and tools, not on the function.

Filter with `--module bookings` or `--kind mutation`.

A [private function](/docs/concepts/functions#private-functions), one its module's index doesn't export, is listed with `private` after its kind, under the name `wrap` sees: `bookings.(private) confirmPaid` (the runtime's `bookings.(private)` plus its variable name), or `bookings.<id>` when it sets `id`. A listener, cron or event that no index exports never runs, so it's listed apart:

```txt
bookings.(private) confirmPaid   mutation private   none   Confirm a booking the guest has just paid for

Not registered: no index exports it, so it never runs
NAME                KIND       WHERE
bookings.onPaid     listener   src/bookings/listeners.ts:4:14
```

## show

Everything about one function, listener or event:

```txt
$ logic-sdk show bookings.cancel
bookings.cancel  mutation
Cancel a booking and free its dates
src/bookings/mutations.ts:52:14

policy      member
input       { bookingId: uuid }
output      { id: uuid, propertyId: uuid, status: "pending" | "confirmed" | … }
checks      canCancel
runs        availability.release
emits       bookings.cancelled → no listeners
called by   nothing in this app (an entry point)
```

`checks` lists the `can*` record checks the function calls, directly or through its module's helpers. See [Authorization](/docs/concepts/authorization#record-rules-can).

A listener with a [`when`](/docs/concepts/jobs#only-some-events-when) gets a `when` row (`conditional` in `--json`). When they apply, two more rows show up: `config` lists the [config](/docs/concepts/config) keys the function reads (never their values), and a run that changes the scope says which keys, as in `runs stock.release (scope: actor)`. In `--json` they're `config` and `scopeChanges`.

## graph

Who runs and schedules whom, and who reacts to which event:

```txt
$ logic-sdk graph --module bookings
bookings
├─ cancel    mutation  runs availability.release
│                      emits bookings.cancelled → no listeners
├─ confirm   mutation  runs availability.hold
│                      emits bookings.confirmed → enquiries.winOnBooking, tasks.prepareStay
└─ checkout  action    runs bookings.get, bookings.confirm
```

`schedules` is a `ctx.schedule(...)` in a mutation: the call runs later, as a job. The function it schedules lists the mutation under `called by`.

`--format mermaid` gives a diagram you can paste into a README or a pull request. `--format json` gives nodes and edges.

## The shape it expects

None, past the registry. A module is what your registry imports (`import * as bookings from "./bookings"`) and lists in `createRegistry({ modules })`. From that file the CLI follows what it exports, through `export *`, `export { a as b }` and imports, to where each function is declared, the way your app does. So lay files out however you like: one file, a folder with an `index.ts`, `bookings.ts` next to a `bookings/` folder, or anything else. A renamed export shows under its exported name, the one the registry uses.

The registry file is `src/registry.ts` by default. If yours lives elsewhere, point to it in `package.json`:

```json
{ "logic-sdk": { "registry": "lib/registry.ts" } }
```

Name your definers however you like (`mutation: defineMutation` works): registered functions are matched by their registered names. What no index reaches is found by its definer: a `const` made by a key destructured from `init()` of `logic-sdk`, aliases included. If loading your app throws (a missing environment variable, say), you get `app-load-failed` with the file and line.

## For scripts and agents

- **`--json`** on `list` and `show` (`graph` has `--format json`). Errors come back as JSON too: `{ "error": { "code", "message", "fix" } }`.
- **Exit codes:** 0 when it worked, 1 when the app couldn't be read, 2 for a usage mistake like an unknown name or flag.
- **No colors when piped.** Data goes to stdout, errors to stderr.

## How it knows

Two sources:

1. **Your registry.** The CLI loads your modules (with [jiti](https://github.com/unjs/jiti), so TypeScript and extensionless imports just work) and asks your own `logic-sdk` what's registered: every function, its kind, schemas and listeners.
2. **Your source.** It parses each module with [oxc](https://oxc.rs) and finds the `run(...)`, `emit(...)` and `schedule(...)` calls inside each function, and inside the helpers it calls by name (`findBooking(ctx, id)`), in its own files or the files they import.

Static reading has limits. A call through a method or a callback (`rules.check(ctx)`, `items.map(...)` handing ctx on) isn't followed, a computed call like `run(fns[name], ...)` shows as `(dynamic)`, and a `run` inside an `if` is a possible edge, not a guaranteed one.

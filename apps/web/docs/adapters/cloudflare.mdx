```ts
// worker.ts
import { drizzleAdapter, outbox } from "logic-sdk/drizzle";
import { cloudflareQueue, handleQueue } from "logic-sdk/cloudflare";
import type { Job } from "logic-sdk";

const makeRegistry = (env: Env, ctx: ExecutionContext) => {
  const db = drizzle({ client: postgres(env.HYPERDRIVE.connectionString, { max: 5 }) });
  return createRegistry({
    modules,
    database: drizzleAdapter(db),
    waitUntil: (p) => ctx.waitUntil(p),
    jobs: { adapter: outbox(db, { via: cloudflareQueue(env.JOBS) }) },
  });
};

export default {
  fetch: app.fetch,

  // runs each job
  async queue(batch, env, ctx) {
    await handleQueue(makeRegistry(env, ctx), batch);
  },

  // sends what never reached the queue, and delayed jobs once they're due
  async scheduled(_controller, env, ctx) {
    await makeRegistry(env, ctx).jobs.sweep();
  },
} satisfies ExportedHandler<Env, Job>;
```

## Two ways to send

| | Durable | When the job leaves |
|---|---|---|
| `outbox(db, { via: cloudflareQueue(env.JOBS) })` | yes | a row is written in your transaction; after commit it's sent and the row deleted |
| `cloudflareQueue(env.JOBS)` | no | sent after commit; a Worker that dies in between loses it |

- **Through the outbox,** the jobs of one commit go in one send. A send that fails keeps the rows, is reported to `onError`, and the sweep sends them again with backoff. After `maxAttempts` failed sends a row is `failed`, and `registry.jobs.retry(id)` puts it back.
- **Alone,** it's the Rails and Laravel `after_commit` model: fine for jobs you can lose, like a cache warm-up.
- **Pick the outbox for anything that matters.** It needs Postgres (through Hyperdrive on Workers), which you already have for mutations.
- **Sends stay under Cloudflare's limits:** 100 messages and 256 KB per send. A job over 128 KB fails its send with an error that says so: keep payloads to ids.

## The consumer

`handleQueue(registry, batch)` runs each message's job with `registry.jobs.run(body, { attempt: message.attempts })`:

- **`done`, `failed` and `discarded` are acknowledged.**
- **A throw is retried** while the listener has [`attempts`](/docs/concepts/jobs#attempts-and-delay) left, after a backoff (`e^attempt` seconds, the outbox's curve). It overrides `retry_delay`.
- **A job that fails for good is kept:** with the outbox, it's written back as a `failed` row, so you can query it and `registry.jobs.retry(id)` it like any other. That includes a job whose listener was renamed or removed: it fails at once, and `retry(id)` runs it once the code is back.
- **If the Worker dies mid-batch,** the messages it didn't acknowledge come back. If Cloudflare counts that as a delivery (we haven't verified it), a listener with `attempts: 1` would fail them without running. On Cloudflare, give listeners `attempts: 2` or more, or set `max_batch_size: 1`.
- **One message at a time, each acknowledged on its own,** so one failure doesn't redeliver the whole batch.
- **Type the Worker with `ExportedHandler<Env, Job>`,** so `batch` carries jobs. A producer and a consumer can be the same Worker, as above, or two.

## Set `max_retries` to at least your largest `attempts`

The listener's `attempts` decide when a job has failed, and Cloudflare's `max_retries` (default 3, so 4 deliveries) caps how often it redelivers. Set `max_retries` at least as high as your largest `attempts`, so Cloudflare never gives up first. The extra delivery is also what lets a last try that crashed be recorded as `failed`.

Things to know:

- **A dead-letter queue is optional.** With `max_retries` set right, it only catches what couldn't be recorded (the outbox was unreachable when the job failed). Without one, Cloudflare deletes those for good, and only `onError` saw them. Messages in a dead-letter queue without a consumer are kept for four days.
- **`delay` goes out as `delaySeconds`,** up to Cloudflare's 24 hours. Through the outbox, the row holds longer delays itself; alone, `createRegistry` refuses a listener with a longer one.
- **Alone, there's nowhere to keep failures:** a job that fails for good is acknowledged and only reported to `onError`.
- **A job can run twice, even at once.** A send that lands but whose row isn't deleted is sent again. A listener that charges or emails should record `ctx.event.id` and skip it if it has seen it.

```ts
// registry.ts
import { PgBoss } from "pg-boss";
import { drizzleAdapter } from "logic-sdk/drizzle/pg";
import { pgBoss } from "logic-sdk/pg-boss";

export const boss = new PgBoss(process.env.DATABASE_URL!);
boss.on("error", console.error);

export const registry = createRegistry({
  modules,
  database: { adapter: drizzleAdapter(db) },
  jobs: { adapter: pgBoss(boss), scope: { store, load } }, // who a job runs as: see Jobs
});
```

Any database adapter that runs SQL (`query`) works, Drizzle or [your own](/docs/adapters/other-orms): pg-boss inserts its jobs through it, in your mutation's transaction.

```ts
// every process that enqueues or works, before it handles anything
await boss.start();

// worker.ts: a queue and workers for every listener and cron, one for scheduled calls, and the cron tick
import { work } from "logic-sdk/pg-boss";
await work(registry, boss);
process.on("SIGTERM", () => boss.stop()); // stops the workers and the tick; waits for running jobs, 30 s at most
```

pg-boss 12, Postgres, and any database adapter that runs SQL (`query`). pg-boss lives in your database, so its insert commits or rolls back with your writes, like Oban: no outbox, and no sweep.

- **Start it in every process,** the web ones too: pg-boss throws on an insert before `boss.start()`.
- **Same database as `database`:** jobs are inserted through your mutation's transaction, with your adapter's `query`. `createRegistry` throws without `database`, or with one that has no `query`.
- **One queue per listener and per cron,** named by its id with a prefix (`logic-sdk.notifications.send`), so each has its own workers and tuning, and none collides with your own pg-boss queues. Scheduled calls share one, `logic-sdk.calls`, so a function doesn't need a worker of its own. `work()` creates them; a process that enqueues first creates the one it needs (on Postgres; on PGlite, with one connection, run `work()` first).
- **`work()` ticks your crons every minute** in each worker process. A cron's minute is one job id everywhere, so several workers ticking it insert one row: no `startTicking` needed.
- **Failed jobs stay in pg-boss** (`state = 'failed'`) for the queue's `deleteAfterSeconds` (7 days by default), with the error as the job's `output`. Query them with pg-boss (`boss.findJobs`): `registry.jobs.failed()` throws here, since pg-boss lists jobs one queue at a time. `registry.jobs.retry(id)` puts one back until pg-boss deletes it, and `registry.jobs.forget(id)` deletes it sooner. `pgBossId(id)` turns a logic-sdk job id into pg-boss's.
- **Rename a listener and its old queue has no worker:** pg-boss deletes those jobs unrun when they expire (14 days). `work()` reports a `logic-sdk.` queue with jobs and no listener to `onError`. Give it its old [`id`](/docs/concepts/jobs#ids) back, or delete the queue.

## Tuning

```ts
const { listener } = init<{ scope: Scope; meta: PgBossMeta & AppMeta }>();

export const sendReceipt = listener({
  event: () => orders.placed,
  attempts: 3,
  meta: { pgBoss: { queue: { expireInSeconds: 120 }, worker: { localConcurrency: 5 } } },
  async handler(ctx, { orderId }) { ... },
});

await work(registry, boss, {
  calls: { worker: { localConcurrency: 10 } },   // the scheduled calls' queue: one at a time by default
});
```

- **`queue`** is pg-boss's queue options (`expireInSeconds`, `retryDelay`, `retryDelayMax`, `deleteAfterSeconds`, `deadLetter`…), applied by `work()` each time it starts. pg-boss copies them onto each job when it's inserted, so a change applies to jobs queued after it. Removing one doesn't reset it: set it back. `partition` only applies when the queue is created, and a `deadLetter` queue must exist first (`boss.createQueue`).
- **`worker`** is pg-boss's `work()` options (`localConcurrency`, `batchSize`, `pollingIntervalSeconds`…), for that listener's workers in each process.
- **Not in `meta`:** retries (a listener's `attempts` decide them, with pg-boss's exponential backoff always on) and the queue `policy`. A cron takes the same `meta.pgBoss` as a listener, for its own queue.
- **Set `expireInSeconds` above your slowest listener** (pg-boss's default is 15 minutes). A job still running then counts as crashed, and pg-boss runs it again. The calls queue is shared, so set it for your slowest scheduled call, or use `heartbeatSeconds`.

## What differs from databaseQueue

- **Attempts are stamped at insert,** as pg-boss's `retryLimit` (`attempts`, one more than its retries: see the last try below), like every adapter: a deploy that changes `attempts` applies to jobs queued after it. `ctx.event.attempt` is pg-boss's retry count plus one.
- **A failure with tries left** goes back to pg-boss, which retries it after a backoff (1 to 2 s, then 2 to 4 s, doubling). **Failed for good** (out of tries, or a domain error other than `conflict`) is pg-boss's `deadletter`: no more retries, and the job moves to the queue's `deadLetter` if you set one.
- **`retry(id)` gives a fresh set of attempts,** like `databaseQueue`, Laravel and Solid Queue; pg-boss's own `retry` gives one more. It only takes failed jobs, and returns `false` otherwise.
- **A crash on the last try** comes back once when `expireInSeconds` runs out, and is failed without running again and reported to `onError`, one backoff later. On an earlier try, pg-boss retries it.
- **`replace`** deletes the waiting call (pg-boss's `created` state) in your transaction and inserts the new one under its own id. A call that started (`active`, or `retry` after a failure) isn't touched.
- **No per-key order yet:** jobs run in parallel per queue, as pg-boss's workers fetch them.
- **At least once,** like every adapter: a listener that charges or emails should keep `ctx.event.id` in a record of its own (two listeners share an event's id) and skip it if it has seen it.

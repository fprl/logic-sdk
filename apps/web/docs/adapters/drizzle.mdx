```ts
import { drizzleAdapter } from "logic-sdk/drizzle";

createRegistry({
  modules,
  database: drizzleAdapter(db),
});
```

`drizzleAdapter(db)` takes any Drizzle database with interactive transactions: node-postgres, postgres.js, PGlite, Neon (websocket), Hyperdrive, better-sqlite3, libsql and others.

## Types

```ts
import type { DrizzleReader, DrizzleTx } from "logic-sdk/drizzle";

// What mutations get: the transaction
type Tx = DrizzleTx<typeof db>;

// What queries get: no insert, update, delete or execute
type Reader = DrizzleReader<Tx>;
```

## Retries

The adapter tells the registry which failures are worth retrying: Postgres deadlocks (`40P01`) and serialization failures (`40001`). See [Transactions](/docs/concepts/transactions#lost-races-are-retried).

## `sqlState`

Reads the SQLSTATE code of a database error, even when Drizzle wraps it. Use it to map constraint violations to [domain errors](/docs/concepts/errors#database-errors).

## Outbox

Events that must not be lost (a receipt, a webhook) go through the outbox: each delivery is a row written in the mutation's transaction, so a committed event always has one. Postgres, Drizzle 1.0.

```ts
// db/schema.ts: drizzle-kit adds the table to your migrations
export { outboxTable } from "logic-sdk/drizzle";

// registry.ts
import { drizzleAdapter, outbox } from "logic-sdk/drizzle";

export const registry = createRegistry({ modules, database: drizzleAdapter(db), jobs: { adapter: outbox(db) } });

// a cron or an interval: what a crash or a failure left behind
await registry.jobs.sweep();
```

On Workers, build it per invocation and sweep from a Cron Trigger:

```ts
export default {
  fetch: app.fetch,
  scheduled: (_controller, env, ctx) => ctx.waitUntil(makeRegistry(env, ctx).jobs.sweep()),
};
```

- **After commit, the request runs them** (through `waitUntil` on serverless), and deletes each row once its listener is done.
- **A failure keeps the row** with the error and a backoff (`e^attempt` seconds: 3, 7, 20, 55… about 3.5 hours over 10 tries); `registry.jobs.sweep()` runs it when it's due. After 10 attempts (`maxAttempts`) it's `failed`.
- **A rule saying no is `failed` at once:** a domain error other than `conflict`, or a payload that no longer matches its schema. Retrying can't help.
- **A crash is a lease running out.** A runner owns a row for `lease` seconds (default 300, longer than your slowest listener); after that, `registry.jobs.sweep()` takes it over. Completion writes are fenced, so a slow runner can't undo a newer one.
- **Failed rows are yours to query** with Drizzle (`status = 'failed'`, `last_error`), and `registry.jobs.retry(id)` puts one back in line. It only touches failed rows (a pending one belongs to its runner) and returns `false` when there's none with that id.
- **A discarded job** (`jobs.scope.load` returned `null`) is deleted, and `sweep` counts it as `discarded`. See [Jobs](/docs/concepts/jobs#who-a-job-runs-as).
- **At least once.** A crash between a listener finishing and its row being deleted runs it again, so listeners must be idempotent: dedupe on `ctx.event.id`.

## Not D1, not HTTP drivers

Cloudflare D1 rejects `BEGIN` and `SAVEPOINT`, and HTTP drivers can't hold a transaction open. `createRegistry` refuses to start when there are mutations but no transactional adapter. On Workers, use Postgres through Hyperdrive.

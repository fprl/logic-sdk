```ts
import { drizzleAdapter } from "logic-sdk/drizzle";

createRegistry({
  modules,
  database: drizzleAdapter(db),
});
```

`drizzleAdapter(db)` takes any Drizzle database with async interactive transactions: node-postgres, postgres.js, PGlite, Neon (websocket) and Hyperdrive. For SQLite, see [below](#not-d1-http-drivers-or-sqlite-yet).

## Types

```ts
import type { DrizzleDb } from "logic-sdk/drizzle";

type Config = {
  scope: Scope;
  db: DrizzleDb<typeof db>;
};
```

Queries get a reader (no `insert`, `update`, `delete` or `execute`), mutations the transaction. For a helper outside a ctx, the two sides are `DrizzleReader<Tx>` and `DrizzleTx<typeof db>`.

Without Drizzle, write the two sides yourself: `db: ReadWrite<MyReader, MyTx>`, from `logic-sdk`. A plain `db: MyTx` is what both get, so queries could then write.

## Retries

The adapter tells the registry which failures are worth retrying: Postgres deadlocks (`40P01`) and serialization failures (`40001`). Three tries by default; `drizzleAdapter(db, { transactionAttempts: 5 })` changes it. See [Transactions](/docs/concepts/transactions#lost-races-are-retried).

## `sqlState`

Reads the SQLSTATE code of a database error, even when Drizzle wraps it. Use it to map constraint violations to [domain errors](/docs/concepts/errors#database-errors).

## Database queue

`databaseQueue(db)` makes your database the queue, like Laravel's `database` driver: each job is a row written in the mutation's transaction, so a committed one is never lost (a receipt, a webhook). Your app runs it, with no worker process. Postgres, Drizzle 1.0.

```ts
// db/schema.ts: drizzle-kit adds the table to your migrations
export { jobsTable } from "logic-sdk/drizzle";

// registry.ts
import { databaseQueue, drizzleAdapter } from "logic-sdk/drizzle";

export const registry = createRegistry({
  modules,
  database: drizzleAdapter(db),
  jobs: { adapter: databaseQueue(db), scope: { store, load } }, // who a job runs as: see Jobs
});

// what a crash or a failure left behind: a platform trigger, or on Node
startTicking(registry); // from logic-sdk/node: ticks crons, sweeps every minute
```

On Workers, build it per invocation and sweep from a Cron Trigger:

```ts
export default {
  fetch: app.fetch,
  scheduled: (_controller, env, ctx) => ctx.waitUntil(makeRegistry(env, ctx).jobs.sweep()),
};
```

- **After commit, the request runs them one by one** (through `waitUntil` on serverless), claiming each just before it runs and deleting it once it's done. So a slow or dead listener doesn't spend the others' attempts. What a dead process hadn't claimed, a sweep runs as a first try, from 30 seconds after the mutation.
- **A listener's `attempts` decide its tries** (default 1). Out of them, the row is `failed`. With tries left, a failure keeps the row with the error and a backoff (`e^attempt` seconds: 3, 7, 20, 55…), and `registry.jobs.sweep()` runs it when it's due. See [Jobs](/docs/concepts/jobs#attempts-and-delay).
- **A rule saying no is `failed` at once:** a domain error other than `conflict`, or a payload that no longer matches its schema. Retrying can't help.
- **A crash is a lease running out.** A runner owns a row for `lease` seconds (default 300) and extends that while it works, for up to 15 minutes, as Laravel Cloud does on SQS. When it stops extending, `registry.jobs.sweep()` takes it over. Each claim gets its own `receipt`, and only that one can finish the job, so a slow runner can't undo a newer one, after a `retry(id)` either. A last try that never finished is `failed` without running again, like Laravel's worker. A listener that runs past the 15 minutes counts as crashed: give `lease` a longer time for one. An extension needs a connection, so with a pool of one it waits for a running mutation: a mutation longer than about two thirds of `lease` can lose it.
- **On Workers, a job that runs right after the request has 30 seconds:** that's what `waitUntil` gets after the response. Longer than that, it's killed: `failed` with one attempt, run again by the sweep with more. Give a long listener `delay: 1`, so the Cron Trigger's sweep runs it (15 minutes), or run it through a queue.
- **`delay`ed jobs wait as rows** until they're due, and a sweep runs them. Sweep at least as often as your shortest delay should be honoured.
- **A job whose listener this process doesn't have** (renamed, removed, not deployed yet) uses its attempts, like a missing class in Laravel, then fails with that reason in `last_error`. `registry.jobs.retry(id)` runs it once the code is back.
- **Failed rows are yours to query** with Drizzle (`status = 'failed'`, `failed_at`, and `last_error` with the stack), and `registry.jobs.retry(id)` puts one back in line. It only touches failed rows (a pending one belongs to its runner) and returns `false` when there's none with that id.
- **Same database as `database`:** it writes in your mutation's transaction, so `createRegistry` throws if it's given another one. A queue in another database (another Postgres, Redis) goes behind an [outbox](#outbox).
- **One registry per jobs table.** A sweep takes any due row, so a second registry with other modules on the same table fails the first's jobs as "isn't a registered listener". Different logic on the same data is modules in one registry, told apart by scope and policies. The same registry built again (per request, on several servers) is fine.
- **A discarded job** (`jobs.scope.load` returned `null`) is deleted, and `sweep` counts it as `discarded`. See [Jobs](/docs/concepts/jobs#who-a-job-runs-as).
- **[Crons](/docs/concepts/crons) run once per minute** across servers: re-export `cronRunsTable` next to `jobsTable` when you have crons.
- **At least once.** The work and marking the job done are two writes. A crash between them runs the job again, or marks it `failed` though it worked when it's out of attempts (look before you `retry(id)` it). So make jobs safe to run twice, scheduled mutations and crons included, as in Rails and Laravel. A listener that charges or emails keeps `ctx.event.id` in a record of its own (two listeners share an event's id) and skips it if it has seen it. A mutation uses a key of its own:

  ```ts
  // unique index on credits.orderId: a second run changes nothing
  await ctx.db.insert(credits).values({ orderId, amount }).onConflictDoNothing();
  ```

  Without `waitUntil`, a job also waits for the listeners it triggered before it's marked done, so that gap lasts as long as they run.

## Outbox

`outbox(db, queue)` puts that table in front of another queue. The row is kept only until the queue has the job, then the queue runs it:

```ts
import { drizzleAdapter, outbox } from "logic-sdk/drizzle";
import { cloudflareQueue } from "logic-sdk/cloudflare";

jobs: { adapter: outbox(db, cloudflareQueue(env.JOBS)), scope: { store, load } },
```

- **Same table, same sweep:** re-export `jobsTable` and trigger `registry.jobs.sweep()`, as above. The sweep sends what a crash or a failed send left behind.
- **The jobs of one commit go in one send.** The queue owns retries after that.
- **`maxAttempts`** (default 10) counts failed sends, then the row is `failed`. A listener's own tries are its `attempts`.
- **A job that fails for good in the consumer** comes back as a `failed` row. See [Cloudflare](/docs/adapters/cloudflare).
- **You don't need one to use a queue:** `cloudflareQueue(env.JOBS)` alone works, and loses a job only when the process dies between commit and send.

## Not D1, HTTP drivers, or SQLite yet

Cloudflare D1 rejects `BEGIN` and `SAVEPOINT`, and HTTP drivers can't hold a transaction open. `createRegistry` refuses to start when there are mutations but no transactional adapter. On Workers, use Postgres through Hyperdrive.

Drizzle's better-sqlite3, bun:sqlite, node:sqlite and Durable Objects drivers run transactions synchronously: they commit before an async mutation finishes, so a failed mutation would keep its writes. Drizzle's types reject them in `drizzleAdapter`.

Don't use a local libsql file either, though it typechecks: mutations that overlap fail with `SQLITE_BUSY`, and can leave the database locked ([352](https://github.com/tursodatabase/libsql-client-ts/issues/352), [361](https://github.com/tursodatabase/libsql-client-ts/issues/361)). Remote Turso is untested. Use Postgres for now: the database queue and the outbox need it anyway.

---
title: AI tools
description: Your exposed functions as AI SDK tools, run as the caller, with the same rules as your API.
---

```ts
import { toAITool } from "logic-sdk/ai";
import { generateText, isStepCount } from "ai";

const caller = registry.as(await scopeFrom(request));

const result = await generateText({
  model,
  tools: {
    confirmBooking: toAITool(caller, bookings.confirm),
    priceStay: toAITool(caller, pricing.priceStay),
  },
  prompt: "Confirm Ana's booking for July",
  stopWhen: isStepCount(5),
});
```

`toAITool(caller, fn)` turns one exposed function into an [AI SDK](https://ai-sdk.dev) tool. You name it, like any tool you'd write with the AI SDK's own `tool()`. The input and output schemas are the ones you already wrote, and the tool is typed. Its description comes from `meta: { ai: { description } }`, or `toAITool(caller, fn, { description })` for one call. It's optional, but models pick tools better with one.

## Same rules as everyone else

Every tool call goes through `caller.run`. That means an agent gets exactly what a person with the same scope gets:

- **`authorize` runs.** An agent bound to a guest can't confirm bookings.
- **One transaction per call**, with retries on lost races.
- **Events after commit**, so listeners send the email once the data is safe.
- **Only `expose: true` functions can be tools**, at the type level too.

There's no separate "AI backend" to keep in sync with your API.

## Many tools at once

`toAITools` turns exposed functions into tools named `module_function`: `bookings_confirm`, `pricing_priceStay`. By default it takes the ones marked `meta: { ai: { tool: true } }`:

```ts
import { toAITools, type AIMeta } from "logic-sdk/ai";

// logic.ts: init<{ ...; meta: AIMeta & AppMeta }>()
export const confirm = mutation({ meta: { ai: { tool: true, description: "Use when staff confirm a booking" } }, ... });

const tools = toAITools(registry, caller);
```

The agent door is opt-in. A function you exposed for your UI doesn't become a tool by accident: something has to mark it. To pick by your own rules, pass `filter`; to take descriptions from your own meta, pass `describe`. Both get the registered function, including its [meta](/docs/concepts/meta):

```ts
toAITools(registry, caller, {
  filter: (f) => f.fn.meta?.tags?.includes("agent") ?? false,
  describe: (f) => f.fn.meta?.summary,
});
```

A description resolves in this order: the call's option (`describe`, or `description` on `toAITool`), then `meta.ai.description`, else none.

To tell agent calls apart in your audit log or policies, put it in the scope: `registry.as({ ...scope, via: "agent" })`.

## Asking a person first

Approval is the AI SDK's job, not ours. Use its `toolApproval` option, keyed by tool name:

```ts
streamText({
  model,
  tools,
  toolApproval: { bookings_checkout: "user-approval" },
});
```

The tool runs only after the person approves, and then it goes through `authorize` like any other call.

## What the model sees when a call fails

| Failure | The model gets |
|---|---|
| A domain error (`ctx.errors.reject`, a failed policy...) | Its code and details, e.g. `pricing.min_nights {"minNights":2,"nights":1}` |
| Anything unexpected | `internal_error` only |

Domain errors reach the model on purpose, so it can recover: suggest other dates, ask for a longer stay. Unexpected errors are reported to `onError` (default: `console.error`) and never reach the model's context, so database messages and stack traces stay private.

## Requirements

- `ai` 7 or newer, any provider.
- A schema library that converts to JSON Schema, so the model can read it. Zod 4 does.
